# ТЗ: генератор новых покемонов

> **Статус:** реализовано, включая UI (3.8) — страница `/generate`. Описание реализации — [`docs/pokemon-model.md`](docs/pokemon-model.md#реализация).

## 1. Цель

Добавить в Instapoke создание новых, не существующих в PokeAPI покемонов. Сгенерированный покемон должен быть правдоподобным: его характеристики, типы, способности, рост, вес и опыт подчиняются тем же связям, что и у реальных покемонов. Модель этих связей описана в [`docs/pokemon-model.md`](docs/pokemon-model.md). Это ТЗ ссылается на её разделы и не повторяет цифры.

## 2. Термины

- **Модель** — набор коэффициентов (распределения BST по классам, сдвиги профиля по типам и способностям, пулы способностей, коэффициенты роста, веса и опыта), посчитанный по реальным данным `pokemon_info` / `ability` с `source_id = 0`.
- **Калибровка** — пересчёт модели по текущим данным базы.
- **Класс** — роль покемона: стадия эволюции, одиночка, полулегендарный, псевдолегендарный, легендарный.
- **Профиль** — доли BST, приходящиеся на каждый из шести статов.
- **Seed** — целое число, от которого детерминированно зависит результат генерации.

## 3. Объём работ

| № | Что | Обязательно |
| --- | --- | --- |
| 3.1 | Калибровка модели: скрипт, считающий коэффициенты из БД в JSON-файл | да |
| 3.2 | Генератор: чистая функция `(model, request, seed) → покемон` | да |
| 3.3 | Генерация цепочек эволюции и mega-форм | да |
| 3.4 | Хранение сгенерированных покемонов в БД | да |
| 3.5 | API: предпросмотр, сохранение, список, удаление | да |
| 3.6 | CLI для пакетной генерации | да |
| 3.7 | Валидатор правдоподобия (те же правила, что у генератора) | да |
| 3.8 | UI: форма генерации и карточка покемона | нет, этап 2 |

Вне объёма: генерация спрайтов, показ сгенерированных покемонов в основной ленте, генерация новых способностей (генератор выбирает только из существующих в `ability`), таблица эффективности типов.

## 4. Калибровка модели (3.1)

### 4.1. Скрипт

`npm run pokemon:model` → `tsx src/server/scripts/fitPokemonModel.ts`.

- Читает `pokemon_info` и `ability` с `source_id = INFO_SOURCES.pokeapi`.
- Пишет `src/server/pokemon-model/model.json` (файл коммитится в репозиторий). Генератор и тесты работают с этим файлом, база для генерации не нужна.
- Печатает сводку: число покемонов и форм, найденные цепочки, ярусы BST, коэффициенты опыта. Если данных меньше 500 базовых покемонов, завершается с кодом 1 и не трогает существующий файл.

### 4.2. Что считает

Алгоритмы — по разделам `docs/pokemon-model.md`.

1. **Разметка классов.** Восстановить цепочки эвристикой из раздела «Классы и BST» (соседние `external_id`, общий тип, общая способность, растущий BST) и пометить стадии. Одиночки с BST ≥ 570 — легендарные или полулегендарные. Финал цепочки из 3 с BST = 600 — псевдолегендарный. Формы (`external_id > 10000`) отделить и сопоставить с корнем по префиксу имени.
2. **BST по классам:** среднее, ст. отклонение, мин., макс.; глобальные запрещённые окна (601–639).
3. **Множители эволюции:** медианы отношений BST, каждого стата, роста и веса между стадиями; доля цепочек с одинаковыми способностями.
4. **Опыт:** для каждого класса — распределение дискретного `k` из набора {0.20, 0.35, 0.45, 0.50} (ближайший к `base_experience / BST`, исключая `NULL` и выбросы > 0.6).
5. **Типы:** частоты основного типа; `P(второй | основной)` и распределение второго типа; средний BST по типу; сдвиги профиля по типу (п.п.); поправка веса по типу (остаток регрессии `ln w` от `ln h`).
6. **Профиль:** средние доли, ковариация долей (для шума), центры архетипов (k-means по долям с k = 6 или фиксированные шаблоны из таблицы архетипов).
7. **Рост и вес:** коэффициенты регрессий `BST ~ ln h` и `ln w ~ ln h`, ст. отклонения остатков.
8. **Способности:** для каждой способности — число носителей, распределение типов носителей, позиция в слотах (слот 1 / 2 / скрытый, при трёх способностях), вектор сдвига профиля (только при 8+ носителях, иначе нулевой), распределение числа способностей по классам. Универсальной считается способность, у которой ни один тип не набирает больше 35 % носителей.
9. **Компенсирующие способности** — не считаются, а задаются вручную в `src/server/pokemon-model/compensation.ts` (таблица из раздела «Способности, которые меняют бюджет»).
10. **Формы:** дельта BST и правила для mega / primal / regional.

### 4.3. Формат

`model.json` описывается Zod-схемой `pokemonModelSchema` в `src/server/pokemon-model/schema.ts`. Скрипт валидирует результат перед записью, генератор валидирует файл при загрузке. В корне файла: `version` (целое, увеличивается при изменении формата), `fittedAt`, `sourceCounts`.

## 5. Генератор (3.2, 3.3)

### 5.1. Интерфейс

```ts
// src/server/pokemon-model/generate.ts
generatePokemon(model: PokemonModel, request: GenerateRequest, seed: number): GeneratedPokemon
generateEvolutionLine(model, request: GenerateLineRequest, seed): GeneratedPokemon[]
generateMegaForm(model, base: GeneratedPokemon, seed): GeneratedPokemon
```

Функции чистые: без БД, сети, `Math.random` и `Date`. Случайность — только через собственный PRNG с seed (например mulberry32) в `src/server/pokemon-model/random.ts`. Один и тот же `(model.version, request, seed)` всегда даёт один и тот же результат.

### 5.2. Запрос (`GenerateRequest`)

Все поля необязательные. Не указанное генерируется по модели.

| Поле | Тип | Ограничения |
| --- | --- | --- |
| `class` | `"stage" \| "single" \| "semiLegendary" \| "pseudoLegendary" \| "legendary"` | |
| `stage` | `{ index: 1..3, of: 2..3 }` | Только при `class = "stage"`, `index <= of` |
| `types` | `string[]` | 1–2 различных типа из 18 известных |
| `archetype` | `"physical" \| "special" \| "tank" \| "fast" \| "hpWall" \| "balanced"` | |
| `bst` | `number` | 175–720, не в запрещённом окне, в пределах яруса класса |
| `abilities` | `string[]` | 1–3 различных имени из `ability` (`source_id = 0`); остальные слоты добираются генератором |
| `name` | `string` | 1–40 символов `[a-z0-9-]`; по умолчанию генерируется |

Противоречивые поля (например `class: "legendary"` и `bst: 300`) — ошибка валидации со списком конфликтов, а не молчаливая подгонка.

### 5.3. Алгоритм

По шагам раздела «Модель генерации» в `docs/pokemon-model.md`:

1. Класс → 2. BST → 3. Типы → 4. Профиль → 5. Способности (и их сдвиг профиля, компенсация) → 6. Статы → 7. Рост и вес → 8. Опыт.

Обязательные требования к шагам:

- **BST:** округление до 5; запрещённые окна; поправка типа не выводит за ярус класса.
- **Способности:** число по распределению класса; слот 1 — типовая способность основного типа; без повторов. При выборе компенсирующей способности применяется правило из `compensation.ts` (например, для `huge-power` доля атаки не выше 0.12, для `wonder-guard` HP = 1). Если пользователь задал способность, генератор подбирает профиль под неё, а не наоборот.
- **Статы:** сумма строго равна BST; каждый стат в допустимом диапазоне класса; не менее 70 % значений кратны 5.
- **Опыт:** `round(BST × k)`, `k` выбирается из распределения класса.
- **Имя** по умолчанию — детерминированный псевдослог из seed (например `zorvanth`), уникальность проверяется при сохранении (п. 6).

### 5.4. Цепочки и формы

- `generateEvolutionLine({ length: 2 | 3, types?, archetype?, abilities? })` строит первую стадию по классу `stage 1/length`, затем каждую следующую по множителям из модели. Профиль сохраняется с шумом не больше, чем в реальных цепочках (корреляция долей с предыдущей стадией ≥ 0.85). Способности сохраняются с вероятностью из модели. BST финала не превышает 600.
- `generateMegaForm(base)`: BST +100, HP не меняется, прибавка распределяется пропорционально профилю, одна способность (из пула типа, с предпочтением сильных), `base_experience` +35…+45, имя `<base>-mega`. Mega строится только от финальной стадии, одиночки или полулегендарного.

### 5.5. Результат (`GeneratedPokemon`)

Та же форма, что `PokemonInfo` из `src/server/pokemon-info/sources.ts` (`name`, `types`, `abilities`, `heightDm`, `weightHg`, `baseExperience`, `stats`), плюс:

- `class`, `stage`, `archetype` — что фактически выбрано;
- `seed`, `modelVersion`;
- `explain` — массив коротких строк о принятых решениях (`"bst 520: class stage 3/3, type dragon +25"`, `"ability sturdy: defense share +6pp"`). Нужен для отладки и UI.

## 6. Хранение (3.4)

Новая таблица `generated_pokemon` (`src/server/db/schema/generatedPokemonSchema.ts`, реэкспорт из барреля, `relations` — в `src/server/db/relations/`). В `pokemon_info` генерированные покемоны **не** пишутся: там данные внешних источников, связанные со спрайтами, и `(source_id, name)` там служит ключом связи со способностями.

| Колонка | Тип | Примечание |
| --- | --- | --- |
| `id` | `uuid` PK | `defaultRandom()` |
| `name` | `text` unique | |
| `types` | `text[]` not null | |
| `abilities` | `text[]` not null | Имена `ability.name`, слоты по порядку |
| `ability_source_id` | `integer` not null | Источник способностей, сейчас `INFO_SOURCES.pokeapi`; связь `(ability_source_id, abilities[i])` → `ability` |
| `height_dm`, `weight_hg` | `integer` not null | Единицы PokeAPI |
| `base_experience` | `integer` not null | |
| `stats` | `jsonb` (`PokemonStats`) not null | |
| `class` | `text` not null | |
| `stage_index`, `stage_of` | `integer` nullable | |
| `archetype` | `text` not null | |
| `parent_id` | `uuid` nullable, FK → `generated_pokemon.id`, `on delete set null` | Предыдущая стадия или базовый покемон формы |
| `form` | `text` nullable | `"mega"` и т. п. |
| `seed` | `bigint` not null | |
| `model_version` | `integer` not null | |
| `request` | `jsonb` not null | Исходный запрос, чтобы воспроизвести генерацию |
| `created_at` | `timestamptz` default now | |

Сохранение цепочки — одна транзакция, `parent_id` проставляется по порядку. Схема доходит до БД через `drizzle-kit push`, как и остальные таблицы. `npm run init` таблицу **не** очищает (как и `pokemon_info`). Имя должно быть уникально среди `generated_pokemon` и не совпадать с `pokemon_info.name`.

## 7. API (3.5)

Контракт — Zod-схемы в `src/shared/api/schema/pokemon/generated.ts`. Как в существующих роутах: `safeParse` запроса (400 со списком ошибок), валидация собственного ответа (500 при несоответствии), ошибки БД логируются и отдаются общим 500.

| Метод и путь | Тело / параметры | Ответ |
| --- | --- | --- |
| `POST /api/pokemon/generated/preview` | `{ request: GenerateRequest, seed?: number, mode?: "single" \| "line" \| "mega" }` | `{ data: GeneratedPokemon[] }` без записи в БД. Без `seed` сервер выбирает случайный и возвращает его в каждом покемоне |
| `POST /api/pokemon/generated` | То же; при том же `seed` результат совпадает с предпросмотром | `201 { data: (GeneratedPokemon & { id })[] }`; `409` при занятом имени |
| `GET /api/pokemon/generated?page=&limit=&types=&class=` | Пагинация как у `/api/pokemon/list` (`infiniteRequest`), `types` — повторяющиеся ключи, AND-семантика | `{ data, pagination: { count, total } }`, порядок `created_at, id` |
| `GET /api/pokemon/generated/[id]` | | `{ data }` или 404 |
| `DELETE /api/pokemon/generated/[id]` | | 204; потомки получают `parent_id = NULL` |

Для `mode = "mega"` в запросе дополнительно нужен `baseId` (сохранённый покемон).

## 8. CLI (3.6)

`npm run pokemon:generate -- [опции]` → `src/server/scripts/generatePokemon.ts`.

| Опция | Смысл |
| --- | --- |
| `--count=N` | Сколько покемонов или цепочек (по умолчанию 1) |
| `--line=2\|3` | Генерировать цепочки указанной длины |
| `--mega` | Дополнительно mega-форму финала |
| `--types=fire,flying`, `--class=…`, `--archetype=…`, `--abilities=…` | Поля запроса |
| `--seed=S` | Seed первого покемона, следующие — `S+1`, `S+2`… |
| `--dry-run` | Печатать JSON и `explain` без записи |

Код возврата 1, если хоть один покемон не сгенерирован или не сохранён. Как и у остальных скриптов, `--` после имени npm-скрипта обязателен.

## 9. Валидатор правдоподобия (3.7)

`validatePokemon(model, pokemon) → { ok, violations: string[] }` в `src/server/pokemon-model/validate.ts`. Применяется к каждому результату генератора (нарушение — ошибка генератора, а не ответ пользователю) и в тестах. Проверяет:

- сумма статов равна BST; BST в ярусе класса, не в запрещённом окне;
- каждый стат в диапазоне класса; не менее 70 % значений кратны 5;
- типы известны и различны; способности существуют в модели, без повторов, их число допустимо для класса;
- слот 1 — способность, у которой основной тип встречается среди носителей (кроме явно заданных пользователем);
- `base_experience = round(BST × k)` для `k` из набора класса;
- рост и вес в пределах ±3σ регрессий модели;
- для цепочки: множители BST в пределах ±2σ модели, корреляция профилей ≥ 0.85, BST финала ≤ 600;
- для mega: ΔBST = 100, ΔHP = 0, одна способность.

## 10. UI (3.8, этап 2)

Отдельная страница `/generate` (не в ленте): форма полей `GenerateRequest`, кнопки «Сгенерировать» (preview) и «Сохранить», карточка с шестью статами (столбики), типами, способностями (`displayName` и `shortEffect` из `GET /api/pokemon/abilities`), ростом и весом в м/кг, а также раскрываемым списком `explain`. Кнопка «Ещё вариант» меняет seed. Компоненты оборачиваются в `memo`, классы объединяются через `@lib/tailwind-merge`; в Tailwind действует `--spacing: 1px`.

## 12. Тесты и критерии приёмки

Unit (`tests/unit/`, без БД):

1. **Детерминизм:** один seed — побайтно одинаковый результат; разные seed дают разные покемоны.
2. **Статистика:** 5000 покемонов без ограничений. Все проходят `validatePokemon`. Средние доли статов отличаются от модели не больше чем на 1 п.п. Доля двойных типов 0.51 ± 0.05. Корреляция `defense ↔ specialDefense` ≥ 0.35. Корреляция `defense ↔ speed` в диапазоне −0.15…0.15. Корреляция `BST ↔ ln(height)` ≥ 0.55. Распределение числа способностей по классам отличается от модели не больше чем на 10 п.п.
3. **Типы → профиль:** 1000 покемонов `types: ["rock"]` — средняя доля defense выше общей минимум на 4 п.п., speed ниже минимум на 2 п.п.
4. **Способности → профиль:** при заданной `sturdy` средняя доля defense выше, чем без неё; при `huge-power` доля атаки ≤ 0.12; при `wonder-guard` HP = 1.
5. **Цепочки:** 500 цепочек из 3 — медианные множители BST 1.33 ± 0.05, BST финала ≤ 600, корреляция профилей ≥ 0.85.
6. **Mega:** ΔBST = 100, ΔHP = 0, одна способность.
7. **Ошибки запроса:** противоречивые поля и неизвестные тип или способность дают ошибку со списком нарушений.
8. **Калибровка:** `fit()` на фиксированном наборе строк даёт ожидаемые коэффициенты; на текущей базе, выгруженной в фикстуру, — значения из `docs/pokemon-model.md` с точностью округления.

Integration (`tests/integration/`, база `instapoke_test`, `seed()` из фикстур):

9. `POST preview` не пишет в БД; `POST` с тем же seed сохраняет тот же результат; повтор имени даёт 409.
10. Цепочка сохраняется одной транзакцией с корректными `parent_id`; `DELETE` родителя обнуляет `parent_id` потомков.
11. `GET` с фильтром `types` — AND-семантика и `total`, как у `/api/pokemon/list`; невалидный запрос — 400.

Общие критерии: `npm run lint`, `npx tsc --noEmit`, `npm test` и `npm run build` проходят. `docs/pokemon-model.md` дополнен разделом о реализации (файлы, команды, формат `model.json`), в `docs/README.md` и `docs/api.md` описаны новые эндпоинты.

## 13. Риски и решения по умолчанию

| Вопрос | Решение по умолчанию |
| --- | --- |
| Эвристика цепочек ошибается на ветвящихся эволюциях | Допустимо: такие покемоны попадают в одиночки; модель устойчива к этому шуму |
| Неизвестен слот скрытой способности при двух способностях | Для статистики слотов учитываются только покемоны с тремя способностями |
| Способности с малым числом носителей | Сдвиг профиля нулевой, участвуют только через привязку к типу |
| Изменились данные PokeAPI | Перезапуск `npm run pokemon:model`, `model.version` не меняется, если не менялся формат; старые записи воспроизводятся по `request` + `seed` только при той же модели |
| Генерация «сломанных» комбинаций (компенсирующая способность у легендарного) | Запрещено правилами `compensation.ts`, кроме явного запроса пользователя |
